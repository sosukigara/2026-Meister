# タスク定義テンプレート — Meister

> AI に新規機能を依頼する際、仕様漏れを防ぐためのフォーマット。コピーして使う。

## テンプレート

```markdown
# タスク: <機能名>

## 背景 / 目的
- なぜこの変更が必要か（1〜3 行）。
- 関連するゴール: G1 自動走行 / G2 アーム回収 / G3 手動操縦（[docs/やりたいこと.md](やりたいこと.md)）

## 入力・出力の仕様
- 入力: <型・範囲・単位>
- 出力: <型・範囲・単位>
- エラー時: <返す値 / 例外 / err_flag>

## 受入基準（Acceptance Criteria）
- [ ] テストがすべてパスすること（`pio test -e native` / `pytest`）
- [ ] 実機 `comm_check` 3 手順が PASS すること（実機挙動を変える場合）
- [ ] 4 通りのビルドが通ること
- [ ] 1 ファイル 300 行以内を維持すること
- [ ] 未検証項目を「✗ 未検証」と明記すること

## 検証コマンド
- <具体的なコマンド>

## 影響範囲
- 変更するファイル / モジュール
- 破壊的変更の有無（軸数・ピン・プロトコル）
```

## 運用のポイント

1. **「コードを読めばわかること」は書かない** — 関数の実装内容や全ファイル一覧を長々と書くとノイズになり、指示が薄まる。
2. **検証可能な形で書く** — 「保守性の高いコードを書く」ではなく「1 ファイル 300 行未満」「関数は単一責務で 20 行以内」のように判定できるルールにする。
3. **レビューで 2 回同じ指摘をしたら追記する** — AI が同じミスを 2 度繰り返した項目だけを `pitfalls.md` や `AGENTS.md` の NG リストに追加していく。ドキュメントが自然と最適化される。
