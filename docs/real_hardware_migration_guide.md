# 実機移行に向けた作業まとめ (Gazeboから実機への置き換え)

現在、Gazeboシミュレーターベースで動作しているSLAMおよびNav2のシステムを実機のロボットに適用するために必要な作業のまとめです。

## 1. 必須データの用意（ROSトピックとTF）

Nav2とSLAM（slam_toolbox）を実機で動かすには、現在シミュレーター（`ros_gz_bridge`）が提供しているデータを、実際のセンサーとマイコンから供給する必要があります。

### 必要なROSトピック
* **`/scan`** (`sensor_msgs/msg/LaserScan`)
  * **役割:** 障害物検知（コストマップ生成）とSLAM（地図作成）用。
  * **やること:** LakiBeamなどの実機LiDARのROS 2ドライバパッケージを起動し、このトピックをパブリッシュさせる。
* **`/odom`** (`nav_msgs/msg/Odometry`)
  * **役割:** 車輪の回転に基づく自己位置推定（相対的な移動量）。
  * **やること:** STM32（モーター制御マイコン）からエンコーダ値を取得し、それを元にROS側（またはSTM32側）でオドメトリを計算しパブリッシュするノードを起動する。
* **`/cmd_vel`** (`geometry_msgs/msg/Twist`)
  * **役割:** Nav2から出力される速度指令の受け取り。
  * **やること:** このトピックをサブスクライブし、内容（目標速度）をSTM32に送信（UDP通信等）してモーターを回す通信ブリッジノードを起動する。

### 必要なTF（座標変換ツリー）
* **`odom` → `base_footprint`**
  * **役割:** 地図上での移動を追跡するための基準。
  * **やること:** `/odom` トピックを発行するノード内で、同時にTF（`tf2`）もブロードキャストするように実装する。
* **`base_footprint` → (LiDARのフレーム)**
  * **役割:** ロボットの中心から見て、LiDARがどの位置・角度に取り付けられているかの定義。
  * **やること:** 機体の中心とLiDARの取り付け位置（オフセット）を定義した実機用URDFを用意し、`robot_state_publisher` を起動して静的TF（`/tf_static`）としてパブリッシュさせる。

## 2. パラメータの変更 (`use_sim_time`)

シミュレーションではGazeboの仮想時間を使用していましたが、実機ではPC（Raspberry PiやJetsonなど）のシステム時刻を使用します。

* **やること:** 起動する全ノード（Nav2, SLAM, `robot_state_publisher`など）の `use_sim_time` パラメータを `true` から `false` に変更する。
  * ※実機用のパラメータファイル（既存の `config/real_nav2_params.yaml` など）を利用・編集し、そこで `use_sim_time: false` を一括指定すると管理しやすいです。

## 3. 実機用Launchファイルの作成

Gazeboの起動処理（`gz_sim` や `spawn_robot`、`ros_gz_bridge`）を省き、実機のハードウェア通信用ノードを組み込んだ新しいLaunchファイルを作成します。

**Launchファイルに組み込むノード構成:**
1. 実機URDFの読み込みと `robot_state_publisher` の起動
2. LiDARドライバ（例: `lakibeam1_scan.launch.py`）の起動
3. STM32通信ブリッジ（UDP等の `/odom` 生成・ `/cmd_vel` 送信）ノードの起動
4. SLAMノード（`slam_toolbox`）の起動 ※`use_sim_time:=false`
5. Nav2ノード群の起動 ※`use_sim_time:=false`

## 4. 実機でのチューニングと検証手順

1. **センサーと通信の単体テスト:**
   まずはSLAMやNav2を動かさず、LiDARとSTM32通信（UDPブリッジ等）のみを起動して、RViz上で `/scan` や `odom` -> `base_footprint` のTFが正しく描画されているか確認する。
2. **手動操作でのマッピング:**
   テレオペ（手動操作）で実機をゆっくり動かしながら `slam_toolbox` で地図を作成する。地図に歪みが起きないか（オドメトリの精度が十分か）を確認する。
3. **自律移動のテスト:**
   作成した地図上でNav2を動かし、RVizから「2D Goal Pose」を投げて正しく目的座標へ追従するかテスト。機体の重さやトルクに合わせて、パラメータ（加速度やコストマップのサイズなど）を微調整する。

## 付録: よくある疑問とトラブルシューティング

### TF (Transform) とは？
ロボットの各パーツ（車体、センサー、車輪など）の位置関係を管理する仕組みです。
- **役割**: 「センサーが検知した物体の位置」を「地図上の座標」に自動で変換するために不可欠です。これがないと、ロボットが動いた時にセンサーデータがどこを指しているのか分からなくなります。
- **確認方法**: RVizの「TF」項目を表示させることで、各座標系（map, odom, base_linkなど）が正しく繋がっているか、ズレていないかを視覚的に確認できます。

### LiDARがロボット自身を検知してしまう場合（自己干渉対策）
機体の支柱やバンパーがLiDARに映り込み、目の前に障害物があるように誤認される場合の対策です。

#### 方法A：最短検知距離の制限（まずはこれを推奨）
LiDARのデータのうち、ロボットの半径以内にある反射をすべて「なかったこと」にします。
- **設定内容**: `mapping_nav_params.yaml` の `laser_min_range` や、各LiDARドライバの最小距離パラメータで設定。
- **メリット**: 設定が1箇所で済み、全方位に対して確実に自爆を防げるため、実機調整の最初のステップとして最適です。

#### 方法B：検知角度の制限
特定の方向（例：真後ろの支柱がある10度分だけなど）のスキャンデータをカットします。
- **設定内容**: `laser_filters` パッケージを使用するか、ドライバ側の角度制限パラメータで指定。
- **メリット**: 方法A（距離制限）だとロボットの死角が大きくなりすぎてしまう場合に、必要な方向の視界を確保しつつノイズだけを除去できます。
