# 実カメラ入力で 30Hz 検出を出す（2026-11-26 / RK3588）

## 結論

この機体の USB カメラは **実画像 25 枚/秒** が物理上限だった。推論は
18.7〜28.5 ms（≈35〜53 fps）で余力があるため、C++ ノードに
**固定 30Hz の配信スケジューラ**を追加し、最新フレームを再利用して
`/detections` を 30Hz 近傍で出すようにした。

**「30fps」は検出結果の配信レートであって、31 枚/秒の新しい画像が
来ているわけではない**。25 枚/秒の実入力に対し約 5 回/秒は直前のフレームを
再推論している。これはドキュメント上の制約として明示する。

## カメラが 25fps である証拠

USB デバイス: `1b71:0057 Fushicai USB2.0 Camera`（`/dev/video0`、
UVC / USB2 480M）。対応フォーマットは **YUYV のみ**（MJPEG 無し）。

| 方法 | 要求 | 実測 |
|---|---|---|
| `v4l2-ctl --set-parm=30 --stream-mmap --stream-count=750` | 30 fps | ストリーム中表示 **25.01 fps**、750 フレームに 30.71 秒（≈24.4 fps） |
| `ffmpeg -f v4l2 -framerate 30 -video_size 640x480 -t 20` | 30 fps | `frame= 500`, `time=19.96`, **fps=25** |
| ROS `yolo_grasp_node`（`output_fps:=0`） | カメラ同期 | `/detections` **25.004 Hz** |
| 320x240 / 640x360 で同じく V4L2 直接計測 | 30 fps | どちらも **24.99 fps** |
| `--set-parm=60` | 30 に丸められる | 300 フレーム 12.76 秒（≈23.5 fps）、改善せず |

ドライバは `Frames per second: 30.000 (30/1)` と要求値を返すが、
実際のストリームは 25 枚/秒。なぜ 30 でなく 25 になるかは ★要確認★
（カメラ側クロックまたは UVC の帯域設定）。ソフト側のバッファ数
（1/2/3）と解像度を変えても変わらないことを実測で確認したので、
それらの実験パラメータはコードに残していない。

## 実装（C++）

`ros/src/umeonigiri_vision/src/yolo_grasp_node.cpp`:

- 新パラメータ `output_fps`（double, 既定 `0.0`）。`0` は従来どおり
  カメラ取得に同期した配信。`30.0` を指定すると専用スレッドが
  一定周期で最新フレームを配信する。
- 取得スレッドは最新フレームを差し替えるだけになり、配信と分離した。
- `detection_image` / `grasp_image` は購読者がいるときだけ描画する
  （既存のトピック入力経路と同じ。640x480 の描画を毎回しない）。
- 既存の `detection_fps` ゲートはシミュレーション用で、ここでは 0 のまま。

起動引数:

```bash
# 直接起動（モデルとラベルは install 側の既存パス）
ros2 run umeonigiri_vision yolo_grasp_node --ros-args \
  -p device:=/dev/video0 -p output_fps:=30.0 -p conf:=0.35

# 実機 launch（pc_vision 経由。既定 30Hz、0 でカメラ同期に戻せる）
ros2 launch umeonigiri_autonomy real_robot.launch.py vision_backend:=npu
```

## 実測（output_fps=30.0）

| 項目 | 値 |
|---|---|
| `/detections` 20〜30 秒 | **29.50 Hz**（30 秒連続、window 841） |
| 最大配信間隔 | **0.035 秒**（最終計測。描画ゲート前は 0.090〜0.125 秒） |
| 推論 time | 18.7〜28.5 ms / フレーム |
| 実入力フレーム | 25 枚/秒（上記） |
| ビルド / テスト | `./build.sh` 成功、118 tests 0 failures |

before / after（同じ `ros2 topic hz /detections`）:
`output_fps:=0` で **25.004 Hz** → `output_fps:=30.0` で **29.50 Hz**。
平均が 30 を少し下回るのはスケジューラが 1ms 刻みで判定するためで、
周期自体は 33ms（最大間隔 35ms）に収まっている。

## 試行と失敗

| 試行 | 結果 |
|---|---|
| バッファ数 1 → 2 → 3 | 25Hz のまま。理由: カメラ側が律速（実測で切り分け） |
| 640x480 → 320x240 | 25Hz のまま（推論は 22〜27ms に改善したが入力が律速） |
| 最初の 30Hz スレッド実装 | `has_frame_` を推論スレッドが消費するため配信が 0.41 Hz に落ちた。初回フレーム到着だけ待ち、以降は `latest_` の有無で判定するよう修正 |
| 毎回 640x480 を描画 | 最大間隔 0.125 s。購読者が居るときだけ描画にして 0.090 s に改善 |

## 未検証

- 実機の手先カメラ（型番・マウント・`/dev/video0` の割当て）は ★要確認★。
  ここで使ったのは汎用 PC カメラである。
- 30Hz 配信がアーム制御側で問題ないか（重複フレームの扱い）は ✗ Unverified。
- INT8 量子化の score 0.5 張り付きは従来どおり残る。

## 25Hz 固定と Web UI レートの安定化（2026-11-26 夜）

要求が「30Hz に見せかける」ではなく「実カメラの 25Hz に張り付ける」に
変わったため、既定を 25Hz に戻した。あわせて Web UI の表示レートが
5〜20Hz で揺れていた問題を C++ 側で直した。

| 変更 | 根拠 |
|---|---|
| `output_fps` 既定を 25.0 に（`pc_vision.launch.py` / `real_robot.launch.py`） | 実入力が 25 枚/秒。フレーム再利用による疑似 30Hz をやめる |
| 表示用画像を `annotated_width=320`（既定 320、0 で元解像度）に縮小 | 640x480 の 921KB を best_effort で流すと DDS のフラグメントロスで Web UI の購読が 200〜1500ms 止まった。実測でエンコード自体は 2〜6ms しかかからず、ボトルネックは転送 |
| `VisionCache` の fps 窓を「直近 20 枚」から「直近 2 秒」に変更 | 枚数窓では到達が止まったとき古いサンプルが残り、表示が揺れる |
| Web UI Subscriber の QoS は best_effort を維持 | reliable に変更すると 921KB 画像の ACK 待ちで publisher が止まり 9Hz / 24 秒 stale に悪化（実測）。revert 済み |

最終実測（20 秒、ブラウザの認識モニターを開いた状態）:

| 項目 | 値 |
|---|---|
| `/detections` | **24.731 Hz**（max 間隔 42ms） |
| `/detection_image` | **24.730 Hz**（max 間隔 44ms） |
| Web UI `/api/vision` の fps | **24.6〜24.8**（20 回連続、frame_age 43ms 以下） |
| 表示解像度 | 320x240 |
| ビルド / テスト | 成功、233 tests 0 failures |

一時的に入れたエンコード時間ログは最終コードから削除済み。
`annotated_width=0` にすれば元の 640x480 に戻るが、その場合は上記の
DDS フラグメントロスが再発する（トレードオフを明示）。
