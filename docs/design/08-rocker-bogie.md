# 設計: 6輪ロッカーボギー・ステアリング・モータ制御

> 対象機能: [features/08-rocker-bogie.md](../features/08-rocker-bogie.md) | 作成日: 2026-08-12 | ステータス: 計画中
> 関連ゴール: [G1](../やりたいこと.md#g1-ロッカーボギーロボット自動走行) [G3](../やりたいこと.md#g3-手動操縦も可能)

## 設計メモ

- **ステアリングサーボ**: 種類は要確定（Feetech STS3215 等のシリアルバスサーボ想定）。6個を UART バス1系統でデイジーチェーン接続できる。
- **駆動モータ**: DC ギヤードモータ想定。エンコーダ付きにすると速度制御・オドメトリ精度が上がる。
- **モータドライバ**: ESP32 の PWM 出力からモータドライバモジュール（例: TB6612 / DRV8833 / BTS7960 等）を介して駆動。
- **FOC 案**: MKS ESP32 FOC V2.0（1 台 2 ch）を 3 台使い、PC と USB 3 リンクで 6 輪を回す。ベンチ版は `firmware/foc_rover/` に実装済み。詳細と前提は下記「FOC ドライバ 3 台で 6 輪を回す構成」。
- **走行モード**: 全輪独立操舵により「前進・後進・斜行・超信地旋回」が可能。Nav2 の経路追従と整合させる。
- 電源容量（モータ6個 + サーボ6個 + アーム）の見積もりが必要。

## FOC ドライバ 3 台で 6 輪を回す構成（2026-11-03 追記・ベンチ版実装）

> 前提: MKS ESP32 FOC V2.0（1 台 2 ch）を 3 台、PC と USB で 3 リンク。
> ステータス: **構成案 + ベンチ版実装（`firmware/foc_rover/`）。実機検証は ✗ 未検証**。
> 下記の帯域・skew は計算値で、測定値ではない。

### 構成

```
PC (ROS 2)
 ├─ USB ─ FOC #1 (M0/M1) ─ 前輪 L / R
 ├─ USB ─ FOC #2 (M0/M1) ─ 中輪 L / R
 └─ USB ─ FOC #3 (M0/M1) ─ 後輪 L / R
```

- 2 ch を前/中/後の 3 軸に割り当てるのが配線・役割ともに素直。左右で分けると 1 台
  3 ch が必要になり、2 ch の基板では成立しない。
- M0 と M1 はドライバ素子・電流センサ・I2C バスが独立（M0: bus 0 / SDA 19 / SCL 18、
  M1: bus 1 / SDA 23 / SCL 5）。AS5600 はどちらも 0x36 だがバスが別なので、2 個を
  同じ基板に付けてもアドレス衝突しない
  （[firmware/foc_winch/docs/bringup_notes.md](../../firmware/foc_winch/docs/bringup_notes.md) §1）。
- **ENABLE は M0/M1 とも GPIO 12 で共有**（公式例 `BLDCDriver3PWM(..., 12)` を両 ch に
  渡している）。片 ch だけ disable できない。片輪の故障を隔離するなら電源側で切る。
- 基板は **AP30H80Q のディスクリート MOSFET + ゲートドライバ**で、6A/ch は
  **冷却前提のピーク**（2ch 合計 12A peak）。連続 6A×2 は温度実測が必要（**★要確認★**）。
- 電流センサは **INA240A2 + 10mΩ シャント、ゲイン 50**（公式例
  `InlineCurrentSense(0.01, 50.0, ...)`）。6A で 3.0V、6.6A で ADC フルスケール。
  販売ページには 1mΩ / ±33A と書くものがあり、**実機のシャント刻印を確認**（10mΩ なら
  6A は測定上限ギリギリ、1mΩ ならファームの 0.01 設定が 10 倍ずれる）。

### 成立する根拠と帯域

- USB 3 本は独立リンク。合計 3 × 7 kB/s（50 Hz 運用）≈ 21 kB/s で、USB 側は余裕。
- ボトルネックは各リンクの 115200 bps（8N1 で 11520 B/s）。
  - 現行テレメトリは 1 モータ 1 行 ~70 B。**1 台 2 モータだと 2 行 = ~140 B**。
    100 Hz では 14000 B/s となり、11520 B/s を超えて**入らない**。
  - 50 Hz なら 7000 B/s（61%）。100 Hz を維持するなら 460800（15%）へ上げる。
    921600 は USB-UART ブリッジとケーブル次第で **✗ 未検証**。
  - 2 モータ分を 1 行にまとめても ~130 B なので、100 Hz では同じく足りない。
- 3 リンクは共通時刻を持たない。指令の書き込み順で数 ms の skew が出るが、0.3 m/s
  なら 1 mm 未満。ただし 1 本の write/flush が詰まると他が遅れるので、リンクごとに
  スレッドを分けるか、非ブロッキングで書く。

### 現行 `firmware/foc_winch` とのギャップ（そのままでは使えない）

> NOTE(2026-11-09): 単軸ウィンチ用 `firmware/foc_winch/` は削除済み（テスト用途は
> `firmware/foc_test/` に集約）。以下は 2026-11-03 時点のスナップショットとして残す。

> 2026-11-03: 走行用の `firmware/foc_rover/` を追加した（3 role × M0/M1、ベンチ
> オープンループ、`M/P/V` コマンド、50 Hz 2 行テレメトリ）。AS5600 は未接続なので
> 閉ループはゲートしたまま。詳細は
> [firmware/foc_rover/README.md](../../firmware/foc_rover/README.md)。以下はウィンチ
> との差分と、まだ残っている穴。

- **M1 単 ch・センサレス前提**（ウィンチ）。`firmware/foc_winch` の `FocDrive` は 1 モータ分。
- **閉ループ（`W`）は AS5600 必須**。無いと `O`（オープンループ）だけで、速度制御・
  保持・オドメトリができない。しかも `kOpenLoopTimeoutMs = 10 s` で自動停止し、
  10 秒クールダウンに入る。走行には使えない。
- **起動ごとに `initFOC()`**（`FocDrive::begin()`）。6 モータ分を毎回回すのは時間も
  失敗率も現実的でない → キャリブレーション値を NVS に保存し、ボード ID を持たせる。
  現状は EEPROM 保存を意図的に未実装（[firmware/foc_winch/README.md](../../firmware/foc_rover/README.md)）。
- **プロトコルはテキスト行でチェックサム無し**。`W 2.0\n` 程度なら実用だが、駆動用は
  誤 1 文字が別指令になりうる。バイナリ + チェックサムか、少なくとも行チェックサムを検討。
- **低電圧ゲート 20.0 V**（`kUndervoltageVolts`）。24 V バッテリの負荷降下で誤作動しうる。
  しきい値とヒステリシスは実測で決める（現状 20.0 V は未測定、
  [bringup_notes §8](../../firmware/foc_winch/docs/bringup_notes.md)）。
- **既存のウィンチを壊さない**。`firmware/foc_winch` はウィンチ用として残し、走行用は
  `firmware/foc_rover/` に分けた（R7）。
- **ビルド環境**: `firmware/foc_winch`（espressif32@6.9.0）と `firmware/main_board`（pioarduino）を
  同じ `~/.platformio` でビルドすると、片方のビルドが他方の `tool-esptoolpy` を
  無効化する（[firmware/foc_winch/README.md](../../firmware/foc_rover/README.md) 既知）。走行用を
  別プロジェクトにするなら `PLATFORMIO_CORE_DIR` を分ける。

### 安全（これが無いと「大丈夫」とは言えない）

- **ボード側コマンド watchdog**: 最後の有効指令から 200 ms で 0 へランプ、500 ms で
  disable。PC 側の `cmd_timeout`（0.5 s）だけでは、USB 断・PC 落ちで**最後の速度が
  そのまま残る**。
- **1 本でもリンクが落ちたら 3 台とも停止**。片側だけ回ると旋回する。
- **ハード E-stop**: 24 V を接触器で切る。ファームの停止は補助。
- 起動時は disable。USB ポートを開くと ESP32 がリセットされうる（ウィンチ README の
  既知事項）。回転中に開き直さない。
- 6 輪分の連続電流・基板（AP30H80Q、6A/ch は冷却前提）の温度を実測。**✗ 未検証**。

### USB・列挙（3 枚で必ず踏む）

- `/dev/ttyUSB0..2` の順は再起動・挿し直しで変わる。USB-UART ブリッジが固有シリアルを
  持たない場合 `by-id` が衝突する → **`/dev/serial/by-path`**（ハブの物理ポート）で
  固定し、基板とケーブルに前/中/後のラベルを貼る。
- 役割は基板の NVS に持たせ、起動時に `#ID` を返すと挿し間違いを検出できる。
  コンパイル時固定は 3 ビルド必要で、差し替え時に気づけない。
- `pio run -t upload` は 3 枚挿したままだと誤った基板へ書く恐れ。1 枚ずつか、by-path を
  明示（P8 の M5Stack 誤書き込みと同じ理由）。
- Linux の `ttyUSB` は `latency_timer` 既定 16 ms。100 Hz テレメトリを溜めるので 1 ms に
  下げる（3 ポート分）。現行 `serial_link.cpp` は設定していない。
- 3 リンクを 1 スレッドで順に read すると、1 本のタイムアウトが他を遅らせる。リンクごとに
  スレッドを分ける。

### 電力・グラウンド

- 3 基板 + 6 モータを 24 V 母線から。基板ごとにヒューズとバルクコン。
- PC の USB GND と 24 V PSU の GND が 2 経路にならないよう星状グランド。PWM 電流が
  USB GND に乗ると、切断・リセットとして現れる。
- USB 5 V と基板 5 V の逆流の有無は基板依存 **★要確認★**。
- 6 モータの突入・回生で 24 V が跳ねる。VIN 耐圧と低電圧ゲートを実測。

### 検証手順（この順でゲート）

1. 1 枚 1 モータ: `O 1`（0.30 V）→ `S`、電流と発熱。AS5600 到着後に `C` → `W ±`。
2. 1 枚 2 モータ同時: I2C・電流の相互干渉、BEMF。
3. 3 枚同時: 挿し直し 10 回で列挙が再現するか、各リンクの Hz、1 本抜去で全停止。
4. 台車を浮かせて 6 輪: 指令方向・速度の一致、E-stop。
5. 接地で連続 10 分: 電流・温度・24 V 降下。

### PC 側の変更点

- `meister_serial_bridge` は `serial_port` 1 本前提。MSTE（ステアリング・アーム）1 本 +
  FOC 3 本の**4 リンク**になる。`/cmd_vel` を舵角系と車輪速度系に分けるノード構成が要る。
- 現行 `kinematics.cpp` は自転車モデルで 6 ch に同じ速度を送る。6 輪で旋回すると内外輪の
  速度差が出るため、FOC の閉ループなら車輪ごとの速度を出せる。どのモデルにするかは
  走行方式の決定（上表 #3）待ち。
