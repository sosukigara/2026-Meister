## 読み方

- **計算量は目標内**。8 コアのうち 0.54 コアで、当初の懸念（重すぎる）は解消している。
  ただし load average 17 の環境での値なので、閑散な状態ではさらに下がる余地がある。
- **経路長比 0.817** は RPP が計画より短くカットしていることを示す。追従は滑らかだが、
  障害物際を通る場面がある（最小クリアランス 0.057 m）。
- **クリアランス 0.057 m は接触寸前**。footprint 半長 0.30 m で計算しているので、
  車体端が障害物セルまで 6 cm まで寄った run がある。PR3 ではこの値を最初に改善する。
- **最終誤差 0.298 m** はゴール許容 0.25 m を超える。yaw 許容内でも xy が超える run が
  あるため、ゴール判定の許容値か RPP の減速プロファイルを見直す。

## 再現手順

```bash
# 上の注意点をまとめて面倒みるラッパー。これを使うのが確実。
ros/src/umeonigiri_autonomy/scripts/measure.sh \
  docs/bench/<date>-<name>.json 10 3 <map-id>

# 制御器を変えて測る場合
MEISTER_LAUNCH_ARGS="controller:=mppi" \
  ros/src/umeonigiri_autonomy/scripts/measure.sh docs/bench/<date>-mppi.json 10 1 mppi
```

## 既知の注意点

- `DISPLAY=:1` が必要（未設定だと Gazebo の Qt 初期化が abort する）。
- 計測は launch と同一プロセスツリーで行う（別プロセスからの DDS 可視性が不安定）。
- 計画時間は「受理応答が返ってから `/plan` が届くまで」。受理応答が遅れる場合は
  送信時刻を起点に落とす（負値にしないため）。
