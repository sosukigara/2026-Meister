# 2026-11-19 制御器の比較（PR7）

RPP（設計 D-4 のベースライン）と MPPI を、同じゴール・同じコストマップ・
同じプランナで比べた。制御器だけを差し替えている。

- 切り替え: `MEISTER_LAUNCH_ARGS="controller:=mppi" ./launch.sh --sim warehouse`
- MPPI 設定: `ros/src/ros2_autonomous_nav/config/mppi_overlay.yaml`（ベースに重ねる）

## 結果（10 ゴール × 1 反復）

| 指標 | RPP（採用） | MPPI |
|---|---|---|
| 成功率 | **10/10** | **5/10** |
| 最終誤差 xy | 0.12–0.20 m | **0.037–0.150 m** |
| 走行クリアランス（最小） | 0.059 m | **0.122 m** |
| 所要時間 | 4–9 s | **17–41 s** |

成功した MPPI の run は**精度もクリアランスも明確に良い**。
とくに最小クリアランスは 2 倍（0.059 → 0.122 m）で、
RPP が角を振って寄る問題に対して狙い通りの効果が出ている。

## 採用判断: 現時点では RPP を維持

理由は 2 つ。

1. **成功率 50%**。失敗した 5 run は計画が 1 度も出ず、45 秒のゴール
   タイムアウトで終わっている（走行時間 0.0 秒）。原因は未特定。
2. **所要時間が 3–5 倍**（4–9 秒 → 17–41 秒）。`vx_max: 0.5` を与えているのに
   出ていないため、critic の重みか `PruneDistance` の設定が合っていない可能性が高い。

「速くて確実だが少し寄る RPP」と「正確で余裕があるが遅く失敗する MPPI」の
どちらを採るかは、失敗原因を潰してから判断する。**現行の既定は RPP のまま**。

## 計算量を下げて再試行した結果（不採用）

失敗が「BT スレッドが MPPI の計算で詰まり、次のゴール受理が返らない」ことによる
可能性を確かめるため、`time_steps` 56 → 40、`batch_size` 2000 → 1000 にして
8 ゴールで測り直した。

| 指標 | 当初設定 (56×2000) | 軽量設定 (40×1000) |
|---|---|---|
| 成功率 | 5/10 | **3/8** |
| 最小クリアランス | 0.122 m | **0.030 m** |
| 平均所要時間 | 17–41 s | 35.8 s |

**悪化した。** 計算量が原因ではないと分かったので、記録済みの設定（56×2000）に戻した。
受理が返らない現象は、プランナを含む BT 側の並行性の問題として別途調べる必要がある。

## 補足: `consider_footprint` について

MPPI の `ObstaclesCritic.consider_footprint: true` は、コストマップに
`footprint` が定義されていないと configure で落ちる
（`Considering footprint in collision checking but no robot footprint provided`）。
ベースのコストマップは `robot_radius` 方式なので `false` にして比較条件を揃えた。
車体形状 (0.60 × 0.50 m) での判定は別途の検証課題とする。
