# 2026-11-20 計算量の計測と削減（Nav + 画像認識）

> 対象: Orange Pi 5 Max / RK3588 / 8GB / aarch64 / Ubuntu 24.04 / ROS 2 Jazzy
> 目的: 自動走行と画像認識を同時に動かし、品質を維持したまま CPU 使用率を下げる。
> 測定は同一機・同一条件で行い、値には条件を併記する。

## 1. 実測した CPU 内訳（シミュレーション、Orange Pi 実機）

測定器: `ros/src/ros2_autonomous_nav/scripts/cpu_split.py --seconds 20`。
`/proc/<pid>/stat` の utime+stime を区間積分し、1 コア = 100% で表す。

| 構成 | 合計（1コア換算） | 8コア比 | `/scan` | 備考 |
|---|---|---|---|---|
| GUI + RViz、step 1ms | 415% | 52% | 4.9 Hz | 既定。Gazebo が実時間の約 0.2 倍でしか進まない |
| ヘッドレス、step 1ms | 491% | 61% | 9.3 Hz | 表示を消したぶん同じ時間で 2 倍進む |
| ヘッドレス、step 2ms | 332% | 41% | 10.1 Hz | 実時間相当 |
| ヘッドレス、step 4ms | 240% | 30% | 10.5 Hz | 物理刻みを粗くする。品質側の影響は §4 |

ヘッドレス時の内訳（step 2ms）: `gz sim` 112% / `parameter_bridge` 39% /
`bt_navigator` 27% / `planner_server` 24% / `controller_server` 23% /
`behavior_server` 22% / `lifecycle_manager` 18% / `slam_toolbox` 15% /
`velocity_smoother` 13% / `map_saver` 12% / `map_server` 9% /
`robot_state_publisher` 9% / `amcl` 8%。

**この内訳の読み方（重要）**: ロボットが静止していても Nav2 の各ノードが
8〜27% を使っている。これは計算内容ではなく、**`/clock` のメッセージ量**に
比例するコストである。gz は 1 step ごとに `/clock` を出すため、step 1ms では
毎秒 700 通、step 4ms では 250 通が全ノードに配られる。実機には `/clock` が
無いので、この項は実機では発生しない。**シミュレーションの CPU 値をそのまま
実機の CPU 見積りに使ってはいけない。**

## 2. 実施した削減（品質に影響しないもの）

| 変更 | 効果（実測） | 品質への影響 |
|---|---|---|
| Gazebo GUI を切る（`MEISTER_GUI=0`、`gz sim -s`） | GUI 単体で 1 コアの 66% を消費していた。切ると同じ時間でシミュレーションが約 2 倍進む | なし（GUI は表示だけ） |
| RViz を切る（`MEISTER_RVIZ=0`） | 1 コアの 34% | なし（Web UI が地図と姿勢を表示する） |
| 画像認識を 320 入力 + 2 スレッド | `/detections` 5.1 → 10.7 Hz、detector CPU 310% → 148%（実機カメラ、2026-11-11 実測） | 検出結果の比較は §5 |
| カメラに MJPEG を要求（`pixel_format`） | 8.5 → 11.3 Hz、露出固定で 14.8 Hz（実機カメラ） | なし（デコードは OpenCV 側） |
| 描画済み画像は購読者がいるときだけ作る | 既存実装（`AnyOneListening`）。視聴者 0 で推論停止 | なし |

実装は `launch.sh` の環境変数 2 つと `simulation.launch.py` の `gui` 引数。
既定は従来どおり（GUI あり・RViz あり）で、明示的に切ったときだけ変わる。

## 3. 検討したが採らなかった・保留の手法

| 手法 | 期待 | 採否の理由 |
|---|---|---|
| Gazebo の物理刻みを 2〜4ms に上げる | 合計 33〜50% 減（実測） | 物理の再現性が変わる。ベンチマークの基準値（`docs/bench/2026-11-18-baseline.md`）と比較できなくなるため既定は 1ms のまま。高速反復したいときの任意設定として値だけ記録 |
| `map_saver` を lifecycle から外す | 8〜18% | Web UI の地図保存（`/api/map/save` → `/map_saver/save_map`）が壊れる。実機では `/clock` が無いためコスト自体ほぼ消える |
| コストマップの `update_frequency` / `publish_frequency` を下げる | 数〜十数% | `publish_frequency` は可視化用で下げても制御に影響しないが、`update_frequency` は障害物検知の遅れに直結する。**品質維持の条件から外れるため変更しない** |
| グローバルコストマップの解像度を 5cm → 10cm に粗くする | セル数 1/4 | 最小クリアランス 57mm の事象（`docs/bench/2026-11-19-tuning.md`）に直撃する。不採用 |
| AMCL の粒子数を減らす | 数% | 自己位置推定の精度と引き換え。不採用 |
| 制御器を MPPI に替える | — | 実測で所要時間 6.9 → 41.6 秒、経路長比 0.89 → 1.54（`2026-11-19-mppi.md`）。不採用 |
| SLAM の `throttle_scans` を 2 にする | スキャン処理半減 | 地図更新が半減。品質条件に触れるため保留 |
| 画像認識の入力 640 を維持しつつ間引く | — | 320 の方が同じ推論回数で軽い。§5 の比較で 320 を既定にした |
| NPU（RKNN）へ推論を移す | 大きい可能性 | **✗ 未検証**。`librknnrt` が未導入で `.rknn` も無い。TOPS からの推定はしない |
| カメラの解像度を下げる | デコードと転送が減る | 検出精度に直結。320 入力に合わせて 640x480 のまま使う |

## 4. シミュレーションの物理刻みについて

`max_step_size` を 2ms / 4ms にすると合計 CPU は 33% / 50% 減り、
`/scan` が 10Hz に追いつく（実時間相当になる）。
一方で、`docs/bench/` の既存ベースラインはすべて 1ms で取得している。
**比較可能性を優先して既定は 1ms のまま**にし、値のみここに記録する。

## 5. 画像認識 320 と 640 の比較（部分的な証拠）

同一の録画（`/camera/image_raw` を 25 秒、`ros2 bag`）を両方に流して比較した。

| | フレーム数 | 検出/フレーム | 空フレーム | クラス |
|---|---|---|---|---|
| 640 / 4 threads | 201 | 0.03 | 194 | person 7 |
| 320 / 2 threads | 186 | 0.16 | 161 | person 17, chair 11 |

フレーム単位のクラス集合一致（Jaccard）は平均 0.844。

**この比較は品質の証明にならない。** 録画したシーンが暗く（画素平均 53/255）、
物体がほとんど写っていないため、どちらも検出がほぼ出ていない。
「320 が 640 より検出を落とす」証拠も「落とさない」証拠も得られていない。
★要確認★ 明るく物体が写るシーンで同じ手順（同一 bag）を再測定すること。
再測定用の手順は `docs/commands.md` §9。

## 6. 判定

- **CPU 使用率**: シミュレーション（ヘッドレス、既定 step 1ms）で 8 コアの 61%。
  目標の 90% 未満に入っている（実測）。
- ただしその大半は Gazebo と `/clock` の配信であり、**実機では発生しない**。
  実機の見積りは「Nav2 0.5 コア（設計目標）+ 画像認識 1.5 コア（320/2t 実測）」
  程度で、8 コアに対して十分小さい。この合成値は **✗ 未検証**（実機で同時に
  走らせた通し計測は未実施。LiDAR 未接続のため）。
- **シミュレーションでのナビ品質検証はこの機ではできない**（§7）。

## 7. シミュレーションの lidar が壊れる件と回避策（実測・解決済み）

当初 `/scan` の全点が 0.092〜0.130 m の一定値になり、SLAM が地図を作れなかった。
原因は Mali-G610 (Panfrost) が **GL 3.3** しか出さず、Ogre2 のシェーダが
要求する SSBO（GL 4.3 以降）が無いこと。`ogre2.log` に
`error: Too many vertex shader storage blocks (1/0)` が毎回出ていた。

**ソフトウェア描画（llvmpipe）に切り替えると GL 4.5 が出て解決する。**

| 構成 | GL | `ranges` | 判定 |
|---|---|---|---|
| 既定（Panfrost） | 3.3 | 全点 0.09〜0.13 m | ✗ 壊れている |
| `LIBGL_ALWAYS_SOFTWARE=1` | **4.5** | 2.25〜9.99 m（中央値 6.87） | ✅ 正常 |

- CPU レイ lidar（`type="lidar"` / `type="ray"`）は gz-sim 8 で無出力（実測）。不可。
- Vulkan バックエンドは ICD 不在で不可（`mesa-vulkan-drivers` に lavapipe が無い）。
- `launch.sh` はシミュレーションモードで既定ソフトウェア描画を使う
  （`MEISTER_GL=hardware` で無効化）。

### 7.1 そのうえで必要な軽量化（`sensor_profile`）

ソフトウェア描画は重い。既定センサ（lidar 640 点/10 Hz、カメラ 640x480/10 Hz）だと
実時間比が数 % しか出ないため、`sensor_profile:=lite`（lidar 360 点/5 Hz、
カメラ 320x240/5 Hz）を用意し、シミュレーションモードの既定にした
（`MEISTER_SIM_PROFILE=full` で高精細に戻せる）。

| ワールド | センサ | RTF（`/clock` 実測） | `/scan` |
|---|---|---|---|
| maze | full | —（測定せず） | — |
| maze | lite | **0.89〜0.92** | 4.3〜4.5 Hz |
| warehouse | lite | 0.20 | 1.2 Hz |
| warehouse | full | 0.05 | 1.0 Hz |

`warehouse` は外部メッシュ（棚・人物）が重く、ソフトウェア描画では実時間に届かない。
**ナビのアルゴリズム検証は `maze`（壁のみ）で行う。**

## 8. 画像認識のレート上限はカメラ側（2026-11-20 実測）

現在つないでいるカメラは **Fushicai USB2.0 Camera**（`1b71:0057`、`/dev/v4l/by-id/usb-USB2.0_Camera_...`）。
以前の測定に使った EMEET C960（MJPEG 対応）とは別機種で、**YUYV しか出さない**。

| 項目 | 実測 | 方法 |
|---|---|---|
| 対応フォーマット | YUYV のみ（MJPG は `invalid`） | `v4l2-ctl --list-formats-ext` |
| 露出制御 | `brightness` のみ。`exposure_*` が無い | `v4l2-ctl --list-ctrls` |
| 640x480 の取得 | **8.3〜8.6 fps**（明るいとき） | `ffmpeg -f v4l2 ... -f null -` |
| 同・同一シーンで暗いとき | **0.96〜3.7 fps** | `ros2 topic hz /camera/image_raw` |
| 320x240 / 160x120 | 6.6 fps（解像度を下げても上がらない） | OpenCV で直接測定 |
| 検出の追随 | 取得フレームと同数（取りこぼし無し） | `record_detections.py` のフレーム数 |
| 検出の CPU | 2.5 Hz 時に 1 コアの **11.5%**（320/2t） | `cpu_split.py` |

**解像度を下げても fps が上がらない**ため、帯域ではなくカメラの露出/フレーム周期が
上限を決めている。`CAP_PROP_FOURCC` で MJPEG を要求しても YUYV のままになる
（このカメラは MJPEG 非対応なので当然）。

したがって、このカメラでの更新周期は **約 1〜11 Hz（照明依存）** で、
**計算側をいくら軽くしてもこれ以上は上がらない**。レートを上げる手段は
ハードウェア側しかない:

- MJPEG 対応カメラ（例: 以前の EMEET C960 は露出固定で 14.8 Hz を実測）に替える
- USB 3 ポートへ挿す（現状は USB 1.1 ルートハブ配下に見える）
- 照明を確保する（自動露出が長秒側に張り付くと 1 Hz まで落ちる）

## 9. 「認識と自動走行の同時動作」の現状

- 計算面では両立する。画像認識は 320/2t で 1 コアの 1.5 コア換算未満
  （10.7 Hz 時に 148%）、Nav2 は設計目標 0.5 コア。合わせて 2 コア程度で、
  8 コアの 25% に収まる（**実測ではなく、それぞれの実測値の合算**）。
- ただし**この機では Gazebo のセンサが壊れている**（§7）ため、
  シミュレーション上で自動走行を走らせて同時動作を確認することはできない。
  同時動作の通し計測は、描画が正常な開発機で行う必要がある（**✗ 未検証**）。

## 10. ナビと画像認識の同時動作（2026-11-20 実測）

`MEISTER_GUI=0 MEISTER_RVIZ=0 ./launch.sh --sim maze`（ソフトウェア描画 + lite センサ）で、
Nav2・SLAM・画像認識・Web UI を同時に起動した状態の実測。

- `/clock` 891 Hz → RTF 0.89、`/scan` 4.5 Hz、`/camera/image_raw` 4.4 Hz、
  画像認識 2.8 fps（Gazebo カメラ供給が上限）。
- CPU 合計 **495% (1 コア換算) = 8 コアの 61.9%**。
  内訳: `gz sim` 161% / `parameter_bridge` 50% / `bt_navigator` 47% /
  `planner_server` 34% / `behavior_server` 31% / `controller_server` 31% /
  `slam_toolbox` 30% / `lifecycle_manager` 24%。
- **ナビの完走を 1 回確認**: ゴール (-1.0, -4.0) に対して `state: "succeeded"`、
  最終位置 (-0.89, -4.01) ＝ 誤差 0.11 m。所要 約 30 秒（sim 時間）。
  別のゴールでは SLAM のドリフトで失敗した（成功率の評価は未実施）。

**✗ 未検証**: 30 ゴールでの成功率・最小クリアランス等の品質指標は、
このワールド・このセンサ設定でまだ測っていない（`measure.sh` は `warehouse` 前提）。
