# FIXES 2026-09-27

## 1. ESP32 と PC の通信が構造的に成立していなかった

### 症状

`meister_serial_bridge` を起動しても ESP32 からの応答が一切返らない。
`/cmd_vel` を送っても FB_STATE が `/esp32/state` に出ない。

### 再現

1. `firmware/` を ESP32 へ書き込む（`pio run -e esp32dev -t upload`）
2. `ros2 launch meister_serial_bridge serial_bridge.launch.py`
3. `ros2 topic pub -r 10 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.1}}'`
4. `ros2 topic hz /esp32/state` → 出力されない

### 原因（file:line）

PC 側とファームウェアが、**別々の UART に接続されていた**。

| 側 | コード | 実際のポート |
|---|---|---|
| PC | `src/meister_serial_bridge/launch/serial_bridge.launch.py:12` の既定 `/dev/ttyUSB0` | CP2102N → ESP32 の **UART0** |
| ファームウェア | `firmware/src/main.cpp:535` `Serial2.begin(..., 16, 17)` | **GPIO16/17**（配線なし） |
| ファームウェア | `firmware/src/main.cpp:523` `Serial2.write(...)`（FB_STATE 送信先） | GPIO17（配線なし） |
| ファームウェア | `firmware/src/main.cpp:532` `Serial.begin(115200)` | UART0 = PC が接続しているポート |

つまり PC はバイナリフレームをコンソール用 UART0 に流し込んでおり、ESP32 は
`Serial`（コンソール）を読まないため 1 バイトもパースされなかった。
FB_STATE は GPIO17 から空へ出ていた。

接続しているボードの実測（`esptool chip-id`）:

| `/dev/serial/by-id` | 実測チップ | MAC | 備考 |
|---|---|---|---|
| `usb-Silicon_Labs_CP2102N_...-port0` | **ESP32-D0WD-V3** (rev v3.1) | `14:2b:2f:ee:ba:c4` | `board = esp32dev` と一致。通信検証の対象 |
| `usb-Espressif_USB_JTAG_serial_debug_unit_30:ED:A0:E3:04:38` | **ESP32-P4** (rev v1.3) | `30:ed:a0:e3:04:38` | ユーザー申告では M5Stack。実測チップは P4。**触っていない** |

書き込みポートは `platformio.ini` の `upload_port` / `monitor_port` に by-id パスを
固定してあり、ポート未指定の `pio run -t upload` が P4 側へ誤って書き込むことはない。

`origin/main` の `meister_serial_bridge` の送信経路は正しいが、接続先が存在しなかった。

### 修正

1. `firmware/src/main.cpp`: `MSTE_UART_BACKEND_USB0` ビルドフラグで
   プロトコル UART を `Serial2`（既定）と `Serial`（UART0/USB）へ切り替え可能に。
   ログ出力は `MSTE_LOG` に集約し、usb0 モードでは no-op にして
   同一線上のコンソール出力とバイナリが混線しないようにした。
2. `firmware/platformio.ini`: 配線なしで確認できる `[env:esp32dev_usbuart]` を追加。
   `upload_port` / `monitor_port` を ESP32 の by-id パスに固定し、同時接続された
   ユーザー申告 M5Stack のボード（実測 ESP32-P4 = `/dev/ttyACM0`）への誤書き込みを構造的に防いだ。
3. `src/meister_serial_bridge/meister_serial_bridge/comm_check.py`: ベンチ確認 CLI
   （`meister_comm_check`）を追加。配線なしで双方向通信を検証できる。

### 検証（実機: ESP32-D0WD-V3 / `/dev/ttyUSB0`）

```
$ meister_comm_check --port /dev/ttyUSB0
port: /dev/ttyUSB0  (/dev/serial/by-id/usb-Silicon_Labs_CP2102N_...-port0)  baud: 115200
  [OK] uplink    enc=[-988, -851, -714, -577, -440, -303] state=0x00 error=0x00
  [OK] downlink  CMD_MOTOR_VELOCITY, CMD_STEERING_ANGLE, CMD_ARM_ANGLE, CMD_GRIPPER -> ... error=0x00
  [OK] err_flag  corrupt frame -> error_flags |= 0x08
PASS: PC <-> ESP32 通信を確認しました。
```

`downlink` は 4 種の有効なコマンドを送った直後の FB_STATE にエラーフラグが
立っていないことで確認している（フラグが立つ = フレーム長不一致で破損扱い）。
`err_flag` は意図的に壊したフレームでフラグが立つことを確認しており、
`downlink` の判定基準が機能していることの裏取りになっている。

## 2. FB_STATE 送信周期が 10 Hz 固定で、根拠がなかった

`firmware/src/main.cpp:528` に `kIntervalMs = 100` がハードコードされ、
線路容量に対する根拠も実測値もなかった。

### 修正

`MSTE_FEEDBACK_HZ`（既定 100 Hz）としてビルドフラグへ移動し、実測に基づいて
値を決めた。測定条件と結果は `firmware/README.md` の「通信周期の測定」を参照。

スイープ（`src/meister_serial_bridge/meister_serial_bridge/feedback_hz_measure.py`
= `meister_hz_measure` で再現可能）:

| 指定 Hz | 実測 Hz | p95 [ms] | 欠落 |
|---|---|---|---|
| 50 / 100 / 125 / 200 / 250 | 追従 | 周期の 1.07 倍 | 0 |
| 500 | 500.3 | 7.57（周期の 3.8 倍） | 0 |
| 1000 | 686.9 | 5.68 | 2 |

線路上限は約 686 Hz（理論天井 11520 B/s ÷ 17 B = 677.6 フレーム/s と一致）。
採用は **100 Hz**（線路使用率 14.8%、タイミングが安定した上限 250 Hz の 40%）。

## 3. `serial_bridge.launch.py` の launch 引数名の消失（作業中の取りこぼし）

`DeclareLaunchArgument('serial_port', ...)` の `'serial_port',` を落とし、
`ros2 launch` が `TypeError: missing 1 required positional argument: 'name'`
で落ちる状態になっていた。すぐ修正済み。`ast.parse` と実 launch で確認。

## 4. `MSTE_FEEDBACK_HZ` が 1000 の約数でない値を無警告で受け入れていた

送信間隔は `1000 / MSTE_FEEDBACK_HZ`（整数ミリ秒）なので、指定 400 は 2 ms に
切り捨てられ**設定値より高い 500 Hz で動作していた**。実際に 400 指定 → 500.4 Hz を
実測で確認している。指定値と実効値が食い違うと「Feedback 周期を実測で決めていない」
状態の診断が成立しなくなる。

### 修正

`firmware/src/main.cpp` に `static_assert(1000 % MSTE_FEEDBACK_HZ == 0, ...)` を追加。
1000 の約数（50/100/125/200/250/500/1000）以外はコンパイルエラーになる。

### 検証

```
$ PLATFORMIO_BUILD_FLAGS="-DMSTE_FEEDBACK_HZ=400" pio run -e esp32dev
src/main.cpp:80:39: error: static assertion failed: MSTE_FEEDBACK_HZ must divide 1000
   80 | static_assert(1000 % MSTE_FEEDBACK_HZ == 0,
esp32dev       FAILED
```

## 5. SIGTERM で終了すると停止フレームが送信されなかった

`serial_bridge_node.py` の `main()` は `except KeyboardInterrupt` + `finally` の
構造で、停止フレーム（舵角 0 / 速度 0）を送るのは `finally` だけだった。
SIGTERM（`pkill` / systemd / `ros2 launch` 経由の停止）は Python の既定で
プロセスを即終了させるため `finally` を飛ばし、**ROS 停止時に速度 0 が送られない**
状態になっていた。ロボット側の最後の安全網を失うため直した。

### 修正

`signal.signal(signal.SIGTERM, ...)` で `KeyboardInterrupt` に変換し、Ctrl-C と
同じ経路を通すようにした。`ExternalShutdownException`（rclpy 側の shutdown）も
同じ `except` で受ける。停止フレーム送信直前に INFO ログを 1 行出力し、
実際に送ったことを確認できるようにした。

### 検証（実機）

`ros2 launch` ではなく **node プロセス**に `kill -TERM` を送った場合の launch ログ:

```
[serial_bridge-1] [WARN] [1790515436.958628330] [serial_bridge]: cmd_vel timeout -> stop
[serial_bridge-1] [WARN] [1790515444.457407747] [serial_bridge]: cmd_vel timeout -> stop
[serial_bridge-1] [INFO] [1790515452.853990437] [serial_bridge]: sending stop frames (steering=0, velocity=0)
[INFO] [serial_bridge-1]: process has finished cleanly [pid 479308]
```

`sending stop frames` が出て初めて `finally` に到達した証拠になる（SIGTERM で
プロセスが落ちること自体は修正前と同じ挙動なので、それだけでは証拠にならない）。
同じ実行でウォッチドッグ（`cmd_vel timeout -> stop`）も 2 回発火している。
停止後も ESP32 側は生きており、`kill -TERM` の直後に `meister_comm_check` は
3 手順とも PASS した（停止フレーム送出後も通信路が健全であることの裏付け）。
